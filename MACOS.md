# Сборка и проверка macOS

## Что переносится без изменения

`Game` не зависит от операционной системы: физика, логика ботов, сглаживание,
счёт и управление автоматическим режимом используются из тех же файлов,
что и в Linux. SDL отвечает за Cocoa-окно, события мыши и клавиатуры,
видеодрайвер и масштаб Retina. Выбор Wayland и восстановление floating-окна
Hyprland компилируются только в Linux.

Шрифт находится в `Ping Pong.app/Contents/Resources/assets`.
На macOS `SDL_GetBasePath()` возвращает Resources приложения, а не папку
исполняемого файла. Поэтому приложение не зависит от текущей рабочей папки
и может запускаться из Finder или после перемещения в «Программы».

## Самостоятельная сборка

Нужны Xcode Command Line Tools и CMake 3.20 или новее:

```sh
xcode-select --install
brew install cmake
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel 3
ctest --test-dir build --output-on-failure
open "build/Ping Pong.app"
```

На Mac опция `PING_PONG_BUNDLED_DEPS` включена по умолчанию. CMake скачивает
SDL 3.4.0 и FreeType 2.14.1 из официальных репозиториев, проверяет контрольные
суммы и собирает статические библиотеки. Дополнительные библиотеки FreeType
для сжатых шрифтов, PNG, Brotli и HarfBuzz отключены: Silkscreen — обычный TTF.

Библиотеки входят в исполняемый файл. На компьютере игрока не нужны Homebrew,
SDL или FreeType. Лицензии включаются в `Contents/Resources/licenses`;
лицензия шрифта лежит рядом с ним.

По умолчанию используется архитектура Mac, на котором выполняется сборка.
Минимальная версия системы в стандартной конфигурации — macOS 12.0.
Это deployment target, а не утверждение, что каждая версия от 12 до 15
проверена вручную.

Можно собрать обе архитектуры в одном приложении с соответствующим SDK:

```sh
cmake -S . -B build-universal -DCMAKE_BUILD_TYPE=Release \
  '-DCMAKE_OSX_ARCHITECTURES=arm64;x86_64'
cmake --build build-universal --parallel 3
```

CI выпускает отдельные приложения, проверенные на своей архитектуре;
универсальная конфигурация не входит в текущую CI-матрицу.

## ZIP для передачи другому пользователю

```sh
cmake --build build --target macos-package
```

Результат находится в `build/dist`. Скрипт упаковки:

1. Проверяет через `otool -L`, что остались только динамические зависимости
   из `/System/Library` и `/usr/lib`.
2. Копирует приложение целиком вместе с ресурсами и лицензиями.
3. Добавляет ad-hoc подпись и проверяет её через `codesign`.
4. Создаёт ZIP через `ditto`, сохраняя структуру macOS bundle.

Имя ZIP содержит архитектуру машины-сборщика. Для приведённой выше
универсальной сборки это имя не отражает все архитектуры внутри приложения;
проверить их можно через `lipo -archs` для файла `Contents/MacOS/Ping Pong`.

Ad-hoc подпись не подтверждает личность разработчика и не заменяет Apple
Developer ID / notarization. Gatekeeper может запросить разрешение на запуск
скачанного приложения. Используется обычный механизм macOS «Всё равно открыть»;
скрипт не отключает Gatekeeper и не меняет системные настройки безопасности.

## Вариант с системными библиотеками

Для локальной разработки можно использовать Homebrew-зависимости:

```sh
brew install cmake sdl3 freetype
cmake -S . -B build-system -DCMAKE_BUILD_TYPE=Release \
  -DPING_PONG_BUNDLED_DEPS=OFF -DCMAKE_PREFIX_PATH="$(brew --prefix)"
cmake --build build-system --parallel 3
open "build-system/Ping Pong.app"
```

Такое приложение зависит от библиотек на компьютере разработчика.
Цель `macos-package` доступна только для варианта со встроенными зависимостями.
На Linux системные SDL3 и FreeType остаются вариантом по умолчанию.

## Как проверять без собственного Mac

Workflow `.github/workflows/macos.yml` запускается на GitHub при push в `main`,
при pull request и вручную через `workflow_dispatch`.

Есть две независимые задачи: `macos-15` с Apple Silicon и `macos-15-intel`.
Каждая собирает исходники, выполняет CTest, запускает автоматический сценарий
с настоящим Cocoa-окном, упаковывает приложение и проверяет запуск копии bundle
из другой рабочей папки. ZIP публикуется как артефакт успешной задачи.

CTest проверяет:

- физику, переключение сложности, плавность и симметрию ботов;
- синтетические события SDL, паузу, автоматический режим и выход;
- сохранение размера между двумя запусками с отдельным тестовым файлом.

Два оконных CTest-сценария используют `dummy` / software backend.
Нативные Cocoa-тесты — отдельные шаги workflow, без этих переменных.
Они проверяют открытие окна, обработку событий и сохранение размера между двумя
запусками настоящего окна. Для небольшого виртуального экрана раннера используются
размеры 900 × 500 и 800 × 450. Эти проверки не заменяют игру человеком.

После первой установки на настоящий Mac остаётся проверить вручную:

- жест двумя пальцами и удобство чувствительности прокрутки;
- скрытие курсора при входе и восстановление при выходе из окна;
- изображение на Retina и перенос между мониторами с разным масштабом;
- паузу во время ручного изменения окна и возврат к игре;
- сохранение размера после закрытия и повторного открытия через Finder;
- запуск скачанного ZIP с обычной проверкой Gatekeeper.

Одинаковый исходный код обеспечивает общие правила и параметры игры.
Ощущение прокрутки может различаться из-за системных настроек и самих тачпадов;
полное совпадение пользовательского опыта нельзя подтвердить тестом без ввода
с реального устройства.
